# greenload-forecast

[![CI](https://github.com/mohammadjaminur/greenload-forecast/actions/workflows/ci.yml/badge.svg)](https://github.com/mohammadjaminur/greenload-forecast/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-brightgreen.svg)](LICENSE)
[![Python 3.11+](https://img.shields.io/badge/python-3.11%2B-blue.svg)](pyproject.toml)

GRU-based demand / price / water / carbon forecasting driving a convex MPC scheduler for water- and carbon-aware datacenter workload placement.

Four independent GRU forecasters predict 24-hour-ahead workload, electricity price, water-usage-effectiveness, and carbon intensity across 10 datacenter locations. Those forecasts feed a receding-horizon Model Predictive Control (MPC) scheduler — a convex program solved with `cvxpy` — that decides how much delay-tolerant workload to route to each location each hour, minimizing price subject to fairness caps on water and carbon footprint. Everything is evaluated against a naive persistence baseline and a perfect-foresight offline oracle.

## Key finding

The original version of this pipeline trained its forecaster with teacher forcing but ran it autoregressively at inference time — a classic exposure-bias mismatch that compounds error over the forecast horizon. Fixing that with scheduled sampling (Bengio et al., 2015) closes **34% of the resulting scheduler's optimality gap** relative to a perfect-foresight oracle (from +25.5% to +16.8% above the oracle's cost).

That fix is real but incomplete, and the incompleteness is itself the more interesting result: even after the fix, this GRU-MPC pipeline still doesn't beat a trivial persistence (zero-order-hold) baseline on total scheduling cost (+16.8% vs. +9.3% optimality gap), and the forecasting improvement itself is signal-dependent — it clearly helps the workload and carbon forecasters, is roughly a wash for water, and slightly hurts price's long-horizon accuracy. Forecast accuracy and downstream decision quality turned out not to be the same thing here, and chasing that gap (rather than declaring victory on NRMSE) is the honest next step. Full numbers are in [`results/metrics.json`](results/metrics.json) and plots in `results/figures/`, generated by `python -m greenload.evaluate` — nothing in this README is hand-typed.

## What this is

- A from-scratch, procedurally-synthetic reimplementation of a predict-then-schedule idea for water- and carbon-aware datacenter workload placement.
- **No real trace data anywhere.** Workload, price, water, and carbon signals are all procedurally generated (`src/greenload/data/generate_synthetic_data.py`) with realistic daily/weekly seasonality, autocorrelated noise, and genuinely distinct per-location baselines — fully reproducible from a fixed seed, with no dependency on any private or third-party dataset.
- Four GRU forecasters, one MPC scheduler (`cvxpy`), one naive baseline, one offline oracle — all sharing a single evaluation harness so the comparison is apples-to-apples.
- **Out of scope, deliberately:** an online Lyapunov drift-plus-penalty scheduler that doesn't require predictions at all, and a separate end-to-end differentiable policy-learning approach (a GRU/LSTM that outputs allocation decisions directly, with no explicit forecast step), are both different problem framings worth knowing about but not what this repo is about. This repo is scoped tightly to one story — forecast, then schedule — rather than three.

## Architecture

```
synthetic data generator (no real data, fixed seed)
        |
        v
chronological train/val/test split + z-score normalization
   (train-set statistics only -- test set never leaks in)
        |
        v
4x GRU seq2seq forecaster: workload / price / water / carbon
   trained with scheduled sampling (fixes exposure bias)
        |  closed-loop 24h autoregressive rollout
        v
receding-horizon MPC scheduler (cvxpy)
   minimize price + l1*max_loc(water) + l2*max_loc(carbon)
        |
        v
realized allocation --> compare vs. naive baseline & offline oracle
```

## Quickstart

```bash
git clone https://github.com/mohammadjaminur/greenload-forecast.git
cd greenload-forecast
pip install -e ".[dev]"

make data       # generate synthetic data                 (< 1s)
make train      # train all 8 models (4 signals x 2 modes) (~10-15 min, CPU)
make evaluate   # run the full evaluation pipeline          (~15-20s)
make test       # run the unit test suite                   (~5s)
```

`results/figures/` and `results/metrics.json` are already committed in this repo, generated from the run described above — you can read the results (and this README) without running anything. Trained model weights are not committed (~75MB for all 8 models); run `make train` to regenerate them, e.g. before using `notebooks/demo.ipynb`.

## Engineering fixes

This project reimplements a predict-then-schedule prototype from scratch, informed by several concrete issues found in that earlier prototype. Fixing them honestly — not just describing them — is the point of this repo:

1. **Exposure bias (the headline fix).** The prototype trained its forecaster with teacher forcing but evaluated it with closed-loop autoregressive rollout — its own inline comment on that rollout path read *"the performance is very poor."* That's the textbook symptom exposure bias describes. The fix here is scheduled sampling (Bengio et al., 2015): a 5-epoch pure-teacher-forcing warmup, then a schedule that ramps up the probability of feeding the model its own prediction, capped below 1.0 so training doesn't fully destabilize. Validation loss is always measured under pure teacher forcing (so it stays comparable across runs); the real effect only shows up in closed-loop rollout error (`results/figures/forecast_error_by_step.png`) and the downstream MPC cost — see Key Finding above. The effect is signal-dependent: it clearly helps workload and carbon, is roughly a wash for water, and slightly hurts price's far-horizon error in this configuration — a single shared schedule isn't obviously optimal for every signal, which is a reasonable next thing to tune.
2. **No more hand-typed headline numbers.** The prototype's final comparison charts were literal Python dicts of numbers that didn't match its own freshly-computed output just above them. Here, `evaluate.py` writes every number to `results/metrics.json` exactly once; figures and this README both read from that file.
3. **Chronological train/val split.** The prototype built all overlapping 24h windows, shuffled them, then sliced train/val — since adjacent windows overlap by up to 23 hours, this let near-duplicate windows land in both splits. Here, hours are split by time *before* windowing.
4. **Full test-set evaluation.** The prototype's evaluation used 19 of ~121 available test windows, unexplained. Here, the full test set is used.
5. **One shape convention for all four signals.** The prototype fed its 10-location axis into the GRU as if it were a length-10 *temporal* sequence for three of the four signals (but not the fourth), recurrently processing locations through a shared hidden state as if they were consecutive time steps. Here, every signal folds location into the batch dimension identically, so the model always sees one real time step per call.
6. **Per-signal normalization, not per-signal learning rates.** Workload (~0-8), water WUE (~0.3-3.6), and carbon intensity (~50-840) live on wildly different scales. Training all four with one shared learning rate on raw values without normalizing first causes the large-scale signal to visibly collapse to predicting a near-constant value (I hit this directly while building this repo). The prototype worked around the same underlying problem by hand-tuning four different learning rates instead of addressing the scale mismatch. Here, every signal is z-scored using training-split statistics only, and one learning rate works for all four.
7. **Backlog conservation in the receding-horizon loop.** Within its lookahead window, the MPC solver is free to *plan* to serve this hour's workload later — but only the current hour's decision is ever realized; the rest of that plan is thrown away when the window rolls forward. Any workload the solver planned to defer has to be explicitly carried forward as backlog, or it silently vanishes. Getting this wrong is what produced my first (very wrong) evaluation run, where every learned method looked *cheaper than the theoretically optimal offline oracle* — a physically impossible result that was the tell something was broken. See `run_receding_horizon`'s docstring in `scheduler/mpc.py` and `tests/test_scheduler.py::test_receding_horizon_backlog_stays_bounded`.
8. **No sign-flip hacks.** The prototype patched negative real-world price data with `price[price < 0] *= -1`. The synthetic data generator here floors values at generation time instead, and forecaster outputs are clipped to non-negative before being handed to the solver (a plain linear output layer is otherwise unbounded).

## Limitations

- **Single fixed seed (42), not averaged over multiple runs.** Point estimates, not confidence intervals.
- **Synthetic, procedurally-generated data throughout, by design** — realistic in shape (seasonality, autocorrelation, per-location diversity) but not real grid or workload measurements. Absolute cost numbers aren't meant to be compared to any real deployment.
- **Scheduled sampling's benefit is signal-dependent**, not universal (see Engineering fix #1) — a single shared schedule is a simplification.
- **The fixed GRU-MPC pipeline still doesn't beat the naive persistence baseline on total scheduling cost** (+16.8% vs. +9.3% optimality gap). This is a genuinely useful negative result: forecast accuracy (where the fixed GRU often wins on NRMSE) and downstream decision quality aren't the same thing, and a scheduler's sensitivity to *which* hours a forecast gets wrong matters as much as aggregate accuracy. Closing this gap — e.g. a training objective that weights the scheduling-relevant part of the signal, more training data, or a larger model — is natural future work, not something this repo claims to have solved.
- **MPC backlog/lookback accounting is a heuristic**, matched to the original prototype's formulation, not a provably-optimal control law.
- **cvxpy solver behavior can vary slightly** across platforms and solver-backend versions; exact reproduction of floating-point-level results isn't guaranteed, only the qualitative comparison.
